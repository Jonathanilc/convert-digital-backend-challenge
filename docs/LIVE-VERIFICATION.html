Method

Every check ran against the deployed applications over the public internet from one machine. Limits were shrunk for this machine's IP alone through the temporary-override API, so real 429s, Retry-After values and sliding-window behaviour could be observed within seconds without affecting other visitors. Budgets are read from the server's own RateLimit-Remaining header rather than assumed, because counters deliberately carry across override changes. All overrides and test rooms were removed at the end. Tokens and secrets are redacted. Re-run with make verify-live.

What this complements: the automated suites, run in Docker on every push and in CI against real Redis and real sockets, cover behaviours that cannot be exercised safely on a live system, in particular fail-open / fail-closed under a Redis outage and exactly-limit admission under concurrent requests.

Re-run constraints: the chat server allows 5 logins per IP per 15 minutes and this script uses 3, so run it at most once per 15 minutes; each run also adds about a dozen anonymous requests to this IP's hourly budget on the rate limiter.

Not verified live, and why

  • Fail-open / fail-closed when Redis is unreachable. Would require taking the shared Redis down. Covered by the engine, middleware and API suites with an injected failing client.
  • Atomicity across concurrent instances. The demo runs one Machine. Covered by the store contract suite: 50 parallel requests, exactly 10 admitted, on real Redis.
  • Fixed-window boundary burst. The default rule's 60-minute window is impractical to straddle live; the memory and Redis stores share one contract suite that covers it.
